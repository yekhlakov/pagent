# AI Agent System Overview

## 🤖 Purpose

This program implements a highly modular and autonomous AI Agent designed to function as a versatile system analyst, experienced programmer, business analyst, or technical writer. Its primary purpose is to take a high-level user task and execute a complex, iterative workflow, leveraging a Large Language Model (LLM) and a suite of specialized tools to achieve the desired outcome.

## ⚙️ Principles of Operation

The agent operates on a continuous, context-driven loop:

1.  **Initialization:** Upon startup, the agent reads configuration details from `config/config.json` and establishes connections to all configured external services (LLM, GitLab, Jira, Mattermost). It also initializes a unique, isolated output directory for the current task.
2.  **Tool Discovery:** The `ToolCallRouterTrait` automatically scans all methods within the agent that are decorated with the `LlmTool` attribute. This process dynamically registers the name, description, and required parameters of every available capability, making them available to the LLM.
3.  **The Execution Loop:** The core logic resides in the `Agent::handle()` method. The agent repeatedly executes the following steps until the LLM signals task completion:
    *   **Context Assembly:** It compiles a comprehensive query package, including the system prompt, the initial user task, the agent's running history (`current_context`), and a list of previously cached files.
    *   **LLM Interaction:** This complete context is sent to the configured LLM API.
    *   **Action Processing:** The agent parses the LLM's response. If the LLM requests a specific tool (e.g., `fdir`, `gitlab_file`), the `ToolCallRouterTrait` intercepts this request, executes the corresponding PHP method, and captures the result.
    *   **Feedback Loop:** The output generated by the tool is appended back into the agent's context, allowing the LLM to reason over the new information and decide the next step.
4.  **Persistence:** The `Cache` trait ensures that files generated during the task (e.g., code snippets, reports) are saved to a local cache (`file-cache.json`) and can be retrieved later by the agent, enabling state persistence.

## 🛠️ Required Configuration

The agent is heavily dependent on a valid `config/config.json` file to connect to external resources. Key sections and required variables include:

*   **`agent`**: Defines operational parameters like `timezone` and the `system-prompt` (or `system-prompt-file`).
*   **`llm`**: Requires provider-specific settings (e.g., `local`). This includes `baseUrl`, `authToken`, and `model` name.
*   **`gitlab`**: Credentials and project identification (`baseUrl`, `accessToken`, `project_id`).
*   **`jira`**: Connection details for task management (`apiUrl`, `apiToken`, `customFieldMap`).
*   **`mattermost`**: Connection details for communication (`apiUrl`, `apiToken`).

## 🧭 Available Tools

The agent exposes a comprehensive set of tools, allowing it to interact with local files, external APIs, and version control systems.

| Tool Name | Description |
| :--- | :--- |
| `fdir` | Lists all files and subdirectories within a specified directory in the local file system. Don\`t query directory names like \`.\` and \`..\`! |
| `fread` | Reads the content of one or more specified files from the local filesystem sequentially. |
| `fwrite` | Writes content to a file in the local file system, completely overwriting any existing content. If the file does not exist, it will be created. |
| `fpatch` | Modifies a range of lines of an existing file in the local file system. The replacement starts after the \`prevLine\` and ends just before \`nextLine\`. |
| `cache_save` | If you need to save something to a temp file, call this function. The file is put to a cache and can be retrieved later. |
| `cache_read_latest` | If you need to read your most recently cached file, call this tool. |
| `cache_read` | If you need to read a file you have previously written to file cache, call this function. |
| `finish` | If you have finished your task, call this function to stop the operation and provide the final result. |
| `gitlab_file` | If you need source code for a php entity (class, attribute, interface, trait) in a Gitlab project, use this function to get it by its fully qualified name. |
| `gitlab_blame` | If you need \`git blame\` info for a php entity (class, attribute, interface, trait) in the Gitlab project, use this function to get it. |
| `gitlab_mr_diff` | Retrieves the full diff content for a specific Merge Request (MR) in a Gitlab project. |
| `gitlab_mr` | Retrieves detailed information about a specific Merge Request (MR) in a Gitlab project. |
| `gitlab_mr_comment` | Posts a comment on a specific Merge Request (MR) in a Gitlab project. |
| `gitlab_ls` | If you need to list of all php entities in a namespace in Gitlab project, use this function. Only namespaces under \`\App\` will be available. |
| `jira_task` | If you need to get a Jira task text, use this tool. The task text (along with several additional fields and comments) will be added to your context. |
| `mm_post` | Posts a message to a specific Mattermost channel. |
| `mm_reply` | Posts a reply (comment) to an existing post within a Mattermost channel thread. |
| `mm_channel_posts` | Retrieves a paginated list of posts from a specific Mattermost channel. |
| `mm_thread_posts` | Retrieves all chronological replies/comments within a specific Mattermost thread. |
